## 0. 参照した外部資料と、そこから持ち込む考え方

### A. イージング図鑑（https://easing-catalog.tanosix.com/ja/）
実物を確認したところ、イージングを **12ファミリー** に体系化し、それぞれに
「方向（イン / アウト / イン・アウト）」「パラメータ」「往復モーション比較」「速度曲線表示」を持たせる構造になっています。

| # | ファミリー | 性格 | リリックビデオでの使いどころ |
|---|---|---|---|
| 1 | リニア | 等速（基準） | 比較用。基本使わない |
| 2 | イージーイーズ | 出発／到着の**影響度(%)** で緩急を調整 | 汎用。字幕のイン／アウト全般 |
| 3 | べき乗 | 指数が大きいほど緩急が強い | 落ち着いたAメロ |
| 4 | サイン | 穏やかな緩急 | ふわふわ・キャラの揺れ |
| 5 | 指数 | 極端な速度変化 | 一瞬で出る／消える強調 |
| 6 | 円弧 | 鋭い速度変化 | ワイプ・トランジション |
| 7 | バック | 逆方向への引き・行き過ぎ | ポップイン（溜めてポン） |
| 8 | エラスティック | 減衰しながら振動 | サビの1文字目、キメ |
| 9 | バウンス | 落下と反発 | ビートバウンス |
| 10 | ベジェ自由曲線 | 4つの制御値 | 上級者の自由指定 |
| 11 | バネ | 減衰バネ応答を終点へ正規化 | キャラ登場・ぷるぷる |
| 12 | ステップ | 進捗を N 段階に量子化 | カクカク・コマ送り演出、拍量子化 |

**持ち込む設計思想**（ここが今回の改善の背骨）:
1. アニメーションを「**チャンネル（何を動かすか）× イージング（どう動かすか）× タイミング（いつ・どの順で）**」に分解する。
   現状はこの3つがベタ書きの数式で混ざっている。
2. イージーイーズの「**影響度（出発%・到着%）**」を UI にそのまま採用する。数式を知らなくても、
   スライダー2本で「入りの粘り」「終わりの粘り」を直感的に触れる。
3. **速度曲線を可視化**する。図鑑がやっているように、選んだイージングの曲線をその場でミニグラフ表示。
4. **往復比較**（リニアと並べて見る）を演出プレビューに応用 → 「Before/After 比較プレビュー」。

## 1. 現状把握（v11 の実装棚卸し）

### できていること（想像以上に作り込まれている）
**① 素材読み込み**
- MP3 / タイミングJSON / プロジェクトJSON / フォント(ttf,otf,woff2) / 歌詞txt の読み込み＋**パネル全域D&D**
- **IndexedDB** にフォントと素材(audio/bg/char)を永続化、**localStorage** に4秒ごと自動保存 → リロード復帰
- **タップ打ち込み**（Space、Backspaceで戻す、前後行プレビュー付き）で JSON をアプリ内生成
- `[Verse 1]` 形式の**セクション解析**、`【曲名】` 形式の**クレジット解析**（→ イントロのタイトル画面へ）
- セクション照合は **NFKC正規化＋2パス（順序どおり→順不同）** で繰り返しサビにも対応
- 背景複数枚 / キャラ最大8体、**緑・白背景の自動検出＋クロマキー**（モード・強さを個別変更可）

**② 演出指定**
- **🪄おまかせMV**：BPM自動判定 → 間奏行の自動挿入 → モーション/デコ/配置の自動割り振り → ゾーン表の自動生成 → 切替演出のランダム配置
- **BPM自動判定**：オンセット包絡線の自己相関（70–200BPM探索）＋コムフィルタで1拍目の位相推定。タップ測定も併設
- 歌詞の全体調整：タイミング補正 / 最大表示秒 / 文字送り（1文字ずつ or 一括）
- **行ごとのタイムライン**：モーション5種 × デコ10種 × 配置4種を行単位で個別指定
- **字幕レイアウト**が優秀：文字単位折り返し＋**禁則処理**、空白での2段分割（幅が揃う切れ目を探索）、
  英単語のスペース保持、**キャラの占有矩形を避けた「すきま配置」**（左右交互）、円形アーチ配置
- **セクション単位のゾーン表**：背景/キャラ/位置/サイズ/動き/エフェクトをプルダウン＋**その場でサムネ合成プレビュー**
- **セクション切替演出11種**（多重丸・多重ボーダー・多重ダイヤ・チェックタイル・斜めスライド・下からバブル・雲ポフ・泡ワイプ・ホワイトフラッシュ・円ワイプ）。べた塗りで確実に画面を覆う設計
- 常時エフェクト4種（しゃぼん玉・キラキラ・桜・フレア）＋丸ぽんっ
- ②内**ミニプレビュー**（再生・シーク・行クリックでその瞬間へ）、シークバーにセクション目盛り

**③ 書き出し**
- Canvas 1280×720 / 1920×1080、`captureStream(30)` + `MediaStreamDestination` で **WebM(VP9/Opus)** 録画
- 冒頭0.5秒の無音リードで音のガビつき対策、曲終了で自動保存、録画中はビートランプ非表示

### 構造上の弱点（v12 で効いてくるもの）
| # | 内容 | 影響 |
|---|---|---|
| W1 | **アニメーションが各所ベタ書き**。`drawLyric` の `switch(motion)` 内に `Math.sin/pow` 直書き、`slide` だけ独自 ease 関数 | 演出追加のたびに描画関数が肥大。イージング差し替え不可 |
| W2 | **タイミングが行単位のみ**。文字送りは `interval` を均等割りしているだけで、実際の発音とは無関係 | 「1文字ずつシンクロ」は名ばかり。**カラオケ表現ができない** |
| W3 | **設定の正が DOM**（`gatherSettings()` が `$("bpm").value` 等を読む）。しかも `fxBubbles` 等は `display:none` の隠しinputが実データ置き場 | Undo/Redo・プリセット・複数プロジェクトが作れない |
| W4 | **書き出しがリアルタイム録画**。重い演出でコマ落ち、fps不安定、WebM のみ | 「本格」を名乗るには弱い。MP4 が欲しい／確定30fpsが欲しい |
| W5 | **文字の見た目が固定**：白フチ + 色は `#1B6FA8` / `#E2447E` の2択ハードコード、フォントは全体で1種類 | ビジュアルの個性が出せない |
| W6 | **音の解析が BPM だけ**。波形・スペクトルを使った演出がない | 音ハメ感が出ない |
| W7 | **毎フレーム再計算**：`drawSectionFx` が毎フレーム `sectionBoundaries()`、`drawFx` が毎フレーム `parseRanges()` | 1080p で重くなる。W4 と相乗 |
| W8 | 二重経路：`state.zoneChars`（ゾーン表）と `chars.ranges`（行番号指定）が併存し、前者が優先 | 挙動が読めない。片方が沈黙で無効になる |
| W9 | 死にコード：`drawBackground` の `type="cut"` 固定で分岐が全部到達不能、`motion:"fuwa"` は `MOTIONS` に無く選べない、`charPace` の `"quick"` 互換 | 保守の地雷 |
| W10 | **16:9 のみ**。縦（9:16）・正方形（1:1）なし | Shorts/TikTok/Reels に出せない |
| W11 | Undo なし、行テキストの編集不可（タイミングの微調整もJSON再生成が必要） | 実制作で詰まる |

## 2. v12 のコンセプト

> **「おまかせで完成する」を守ったまま、その下に“本気で詰められる層”を作る。**

3層構造にする：
- **かんたん層（既存の体験を維持）**：3点セット読み込み → 🪄おまかせMV → 書き出し。ここは絶対に壊さない。
- **調整層（新設の主戦場）**：イージング＋モーションを分解して、スライダーで詰められる。
- **プロ層（任意）**：文字単位タイミング、キーフレーム、確定レンダリング。

## 3. 改善案（優先度順）

### ★P0：土台の作り直し（他の全部がここに乗る）

**P0-1. イージングエンジンの導入**（図鑑の12ファミリーを実装）
- `easing.js` 相当のモジュールを HTML 内に新設。`ease(name, dir, params)(t) -> 0..1` の単一インターフェース。
- 実装するもの：`linear` / `easyEase(出発%, 到着%)` / `power(n)` / `sine` / `expo` / `circ` / `back(overshoot)` /
  `elastic(振幅, 周期)` / `bounce` / `cubicBezier(x1,y1,x2,y2)` / `spring(剛性, 減衰, 質量)` / `steps(n, 丸め)`
  × 方向 `in / out / inOut`。
- **既存5モーションを全部この上に載せ替える**（見た目は今と同じになるようパラメータを合わせてから移行）。
  - ポップイン → `back.out`
  - ビートバウンス → `bounce.out` ＋ 拍位相
  - じわズーム → `sine.inOut`
  - 文字弾け → `expo.out` ＋ スパーク
  - スローイン・アウト → `power(4).out` → `power(4).in`（現状の `easeO/easeI` がまさにこれ）
- UI：モーション選択の隣に **イージング選択＋速度曲線ミニグラフ**（図鑑の「速度曲線を表示」相当）。
  「影響度：出発 ○% / 到着 ○%」の2スライダーを既定UIにする（数式を出さない）。

**P0-2. アニメーションのデータ化（チャンネル分解）**
- 演出を数式でなく**データ**で持つ：
  ```
  { channel: "scale"|"y"|"x"|"alpha"|"rotate"|"blur",
    from, to, easing:{name,dir,params}, delay, dur,
    stagger:{ per:"char"|"word"|"row", amount, from:"start"|"center"|"random" } }
  ```
- 「モーション」＝このトラックの配列＝**プリセット**。これで新演出がコード追加なしに増える。
- `stagger`（1文字ずつズラす量と方向）を独立パラメータにする。今は `interval` 一択で中央始まり等ができない。

**P0-3. 状態の一元化**
- DOM ではなく `state` を正にする。DOM は `state` を編集するビューに降格（`gatherSettings` の DOM読みを廃止）。
- 隠しinput（`fxBubbles` 等）を撤去し `state.fx` へ。W8 の二重経路も `zoneChars` に一本化。
- **Undo / Redo**（Ctrl+Z / Ctrl+Shift+Z）：state のスナップショットスタック。実制作で最も効く安心感。
- 死にコード（W9）を除去。

**P0-4. 描画のフレーム前計算**
- 毎フレームの `sectionBoundaries()` / `parseRanges()` を、**編集時に一度だけ**作る「コンパイル済みタイムライン」に置換。
- `state` 変更時に `compile()` → `{ 時刻順イベント配列, 行→ゾーン索引, fx区間 }` を作る。W7 解消＋P1-1の前提。

### ★P1：「本格リリックビデオ」に必要な機能

**P1-1. 確定レンダリング書き出し（最重要）**
- 現状のリアルタイム MediaRecorder に加え、**オフラインレンダリングモード**を追加：
  - `t = frame / fps` で1フレームずつ確定描画（音とは非同期）→ エンコード。
  - コマ落ちゼロ・確定30/60fps。重い演出を入れても品質が落ちない。
- **機能検出で3段階に分岐**（決定事項。Safariも動かす）：
  1. `VideoEncoder` + `AudioEncoder` 両方あり → **フル書き出し**（映像・音声ともWebCodecsでエンコードしMP4へ多重化）
  2. `VideoEncoder` のみ（Safari 16.4〜18.7 相当）→ **映像はWebCodecs、音声は元mp3ファイルをそのまま多重化**
     （デコード＆再エンコードせず、タイムスタンプを合わせて既存の音声ストリームを流し込む）
  3. どちらも非対応 → **現行の MediaRecorder 経路**（リアルタイム録画・WebM）にフォールバック
  - UI上は「Chrome/Edge 推奨」と明示しつつ、Safariでも①か②のどちらかで動く設計にする。
  - 3段階のどれが選ばれたかを書き出し画面に小さく表示（サポート状況の透明性）。
- **MP4(H.264) 出力**：WebCodecs + mp4 muxer（`mp4-muxer` 等、または自前 box 書き出し）。
  YouTube 以外（LINE/X/スマホ）への配布で WebM は詰まりがち。
- 進捗バー（「1234 / 5400 フレーム」）とキャンセル。
- **音の扱い（①のフル書き出し時）**：`OfflineAudioContext` でデコード済み PCM を AAC/Opus エンコードして多重化。

**P1-2. 縦・正方形対応（9:16 / 1:1 / 16:9）**
- `CW/CH` 依存の配置係数を**アスペクト非依存の安全領域計算**に置き換える。
- 字幕ゾーン（`pickZone`）・キャラ配置・トランジションを比率で再定義。
- プリセット：YouTube(16:9) / Shorts・TikTok・Reels(9:16) / Instagram(1:1)。
- 縦では「すきま配置」は左右でなく**上下**を探す、など分岐が要る。

**P1-3. 文字単位タイミング（カラオケ表現）**
- データ拡張：`line.chars = [{c, t}]`（任意。無ければ従来どおり均等割りにフォールバック）。
- 入力手段3つ：
  1. **タップ打ち込みの文字モード**（Spaceで1文字ずつ）
  2. **行内ドラッグ調整UI**（波形の上に文字を並べて左右に動かす）
  3. **自動推定**：行の区間を、モーラ数（拗音・促音・長音を考慮した日本語モーラ分割）で重み付け配分。
     ─ 現状の「等分割」より確実に自然になる。まずここだけでも効果が大きい。
- 表現：**塗り進みワイプ**（カラオケの色変わり）を追加。リリックビデオの定番なのに現状ない。

**P1-4. 波形＆音解析ビュー**
- ②に**波形タイムライン**を表示（`decodeAudioData` 済みのピーク配列を描画）。
  - 行マーカーを波形の上にドラッグで置ける → タイミング微調整が劇的に楽になる（W11解消）。
  - セクション境界・拍グリッドを重ねて表示。
- **周波数解析の演出利用**：低域（キック）で背景が呼吸する、高域でキラキラが増える等。
  - オフラインレンダリングと両立させるため、**再生時FFTではなく事前解析した包絡線配列**を使う（重要）。

**P1-5. 文字ビジュアルの自由度**
- 色：本文色 / フチ色 / フチ太さ / 影 / **グラデーション** / 発光（グロー）。
- **セクションごとのテキストスタイル**（サビだけ色を変える等）＋行単位の上書き。
- フォントを**用途別に3枠**：タイトル / 歌詞 / クレジット。
- 縦書き（`writing-mode` 相当を Canvas で手実装）、ルビ（ふりがな）は将来課題として枠だけ用意。

### ★P2：質を上げる（差が出るところ）

**P2-1. クロマキーのフチ処理**（note記事の「画像端の補間」を応用）
- 現状は緑判定でαを落とすだけ → **フチに緑が残る／ジャギる**。
- 追加：①スピルサプレッション（残留緑を周辺色で置換、現状の簡易版を強化）
  ②αのフェザリング（1〜2px のぼかし）③**ピクセル延長による端の色補間**。
- 全解像度で毎回再計算している `chromaKey` を、プレビューは縮小版・書き出し時のみ原寸にする。

**P2-2. カメラワーク（Ken Burns の拡張）**
- 現状は背景に固定の微ズーム（`1.03+0.02*sin`）のみ。
- **ゾーン単位のカメラ**：ズームイン／アウト／パン方向／回転を、P0-1のイージング付きで指定。
- サビ頭で**拍に合わせた軽いパンチズーム**（`back.out` で 1.0→1.06→1.0）。音ハメ感が跳ね上がる。

**P2-3. トランジションの整理と拡張**
- 既存11種を P0-1 のイージング付きに書き換え（今は全部 `sin(p*PI)` 固定＝全部同じ質感）。
  → 円弧/指数/バックを当てるだけで別物になる。
- 追加候補：ズームブラー、グリッチ、ページめくり、シェイプワイプ（星・ハート）、文字マスク（歌詞の形で抜ける）。
- **背景切替の演出を復活**：現状 `type="cut"` 固定で分岐が死んでいる（W9）。セクション演出と役割分担を決めて有効化。

**P2-4. キャラの「ぷるぷる」メッシュ変形**（note記事の技術を輸入）
- 固定格子メッシュ＋頂点ウェイトで、キャラ画像を**拍に合わせてぷるんと揺らす**。
- Canvas2D では三角形分割＋クリップで近似、または WebGL パスを別途用意。
- 現状の `cmotion`（跳ねる/ふわふわ/静止）に「ぷるぷる」「スクワッシュ＆ストレッチ」を追加。
- ※ 重い可能性があるので、**プレビューは簡易・書き出しは本番品質**の二段構えにする。

**P2-5. モーション／イージング カタログ画面**（note記事の「モーション図鑑」導線）
- アプリ内に「④カタログ」タブ。全モーション × 全イージングをサンプル文字でループ再生。
- クリックで「このモーションを選択中の行に適用」。**機能でもあり、そのまま宣伝素材にもなる**。

### ★P3：使い勝手・運用

- **P3-1. プロジェクト管理**：複数プロジェクトの保存/切替（現在は localStorage に1件のみ・上書き事故のリスク）。

## 8. F1バグ修正（ユーザーテストのフィードバック対応）

実際にブラウザで触ってもらったところ、3件の指摘があり、いずれも修正・動作確認済み。

### 1. 「キャラの登場（行番号で指定）」欄の数字が消える／おまかせMVで割り振られない
**原因（v11から存在する既存の設計問題。PLAN.md冒頭のW8で指摘していた「二重経路」そのもの）**：
「素材タイムライン（セクション表）」でキャラを割り当てると `applySecAssign()` が全キャラの `ch.ranges` を無条件で
空文字にクリアしていた。実際にユーザーがエクスポートした `AI Bubble_project.json` でも全キャラの `ranges` が
空になっていることを確認して裏付けを取った。`visibleChars()` は `state.zoneChars` がある場合は `ch.ranges` を
一切参照しないため、このクリア処理は機能的に無意味と判明。

**対応**：
- `applySecAssign()` から `ch.ranges` のクリアを削除（直接指定欄のデータが消えなくなった）。
- おまかせMV／ゾーン表でキャラを割り当てた場合、「キャラの登場」欄に**素材タイムラインが実際に計算した行番号を
  自動表示**（グレーアウトの読み取り専用）するように変更。「割り振られていないように見える」状態を解消。
  位置／サイズ／動きの選択欄も同様に、ゾーン表が有効な間は読み取り専用表示にした。
- ブラウザ上で「ゾーン割り当て→キャラの登場欄に数字が表示される」ことを確認済み。

### 2. イージングの使い方が分からない／行ごとのモーション選択欄が無くなる
**原因**：F1の初回実装で「イージング指定」を独立した7つ目のモーションとして追加したため、
1行に対して「ポップイン」と「イージングで調整」を同時に選べず、二者択一になっていた。
チーム内では「将来の一文字ずつタイミング対応のためにこうなっているのか」という問いをもらったが、
**そうではなく、既存5モーションを壊さないための一時的な回避策**だった（8-1参照）。今回、本来の設計
（PLAN.md 0章で書いた「モーション＝チャンネル」「イージング＝どう動くか」を分離する方針）に合わせて作り直した。

**対応**：
- 「イージング指定」モーションを削除。モーション欄は元の6種（ポップイン/ビートバウンス/じわズーム/文字弾け/
  スローイン・アウト/ふわっと）に戻った。
- 代わりに②パネルの「🎚 イージング設定」に**チェックボックス**を追加：
  「上のポップイン等モーションの『動き出し方』をこの曲線に差し替える」。
  ONにすると、選んだモーションの見た目（ポップの弾み方、ビートバウンスの跳ね方など）はそのままに、
  **時間の進み方（動き出しの速さ）だけ**が選んだイージング曲線に置き換わる。OFF（既定）なら完全に元の挙動。
- ブラウザ上で、6モーション全てについてチェックON/OFF両方でエラーなく描画できることを確認済み。

### 3. 未解決の確認事項

## 9. 演出タイムライン／素材タイムラインの統合（F2着手）

### 背景
「キャラの登場」「背景の切り替え」の直接指定と「素材タイムライン（ゾーン表）」が並存していたのが、8章のバグの
根本原因だった。ユーザーから「演出タイムラインのように行番号ベースで、素材タイムラインも同じ形にしたい／
いっそ演出も素材も同一タイムラインにしてはどうか」という提案があり、検討の結果こちらの方が前回私が提案した
「ゾーン分割ボタン」案より優れていると判断（行単位なのでセクションタグが無くても機能し、セクション内の
1行だけの細かい制御も自然にできるため）。ユーザーの了承を得て実装した。

### 実装した設計（`ramune-mv-maker-v12.html`）
- **データモデル**：各行に `bg` / `ch` / `chPos` / `chSize` / `chMotion` / `fx` / `pop` を追加。
  値が空文字（未設定）の場合は「ひとつ上の行から引き継ぐ」という**カスケード方式**（CSSのcascadeやPowerPointの
  スライドマスターに近い考え方）。`"none"`は「ここで明示的に解除」を意味する。
  - `fx`（🫧✨🌸🌟の継続エフェクト）もカスケード対象。
  - `pop`（丸ぽんっ）だけは一瞬のイベントなのでカスケードなし（true/falseの単純な行フラグ）。
- **解決ロジック**：`resolveLineField(lineIdx,key)`（背景・エフェクト用、現在行から遡って最初に見つかった値を採用）
  と `resolveCharAt(lineIdx)`（キャラ用、名前が変わった境目より前は見ないようにスコープを切る）を新設。
  `pickBg()`・`visibleChars()`・`drawFx()` をこれらを使うよう全面的に書き換えた。
- **UI**：`renderLineList()` を拡張し、演出タイムラインと素材タイムラインを1つのリストに統合。
  - セクション見出し行・間奏行（前奏/間奏/後奏）＝「まとめ役」：背景／キャラ／位置／大きさ／動き／エフェクトの
    フルセットの選択欄＋**その場で合成した縮小サムネイル**（ここだけ描画コストをかける・懸念点2への対応）。
  - 通常の歌詞行：モーション／デコ／配置に加え、背景／キャラ／エフェクトのコンパクトな選択欄（既定は全部「引継」）。
    キャラの位置／大きさ／動きは `<details>`（🧍詳細）で折りたたみ、行の横幅が広がりすぎないようにした
    （懸念点1への対応）。
  - 旧「素材タイムライン」ゾーン表・「キャラの登場」「背景の切り替え」直接指定欄は完全に削除。
- **おまかせMV**：ゾーン表(`state.secAssign`)への書き込みをやめ、各ゾーンの先頭行に `bg`/`ch`/`chPos`/`chSize`/
  `chMotion`/`fx` を直接セットする方式に変更。丸ぽんっ（`pop`）はセクション頭の行に立てる。
  常時しゃぼん玉は `state.fx.always="bubbles"` に変更（旧・全行レンジ指定"all"相当）。
- **互換性（v11互換は必須の要件）**：`migrateLegacyToLines(s)` を新設し、`applySettings()` から呼び出す。
  1. 旧・ゾーン表形式（`secAssign`あり）→ 各ゾーンの先頭行に変換。
  2. さらに古い直接レンジ指定形式（`chars[].ranges`/`bgs[].ranges`のみ）→ 範囲の開始行に設定・終了の次の行に
     `"none"`を明示的に挿入して引き継ぎを止める、という変換。
  新形式のプロジェクトJSONは`secAssign`もrangesも書き出さないため、読み込み時にどちらの分岐も空振り＝安全。
- **キャラクター/背景オブジェクトの整理**：`ch.ranges`/`ch.pos`/`ch.size`/`ch.cmotion`、`bg.ranges` は行データに
  置き換わったため撤去。`ch.keyMode`/`ch.keyStrength`（クロマキー設定）のみ残した。

ユーザーから「②の『歌詞の全体調整』（歌詞デコ・字幕スタイル）と、タイムラインの『全体のデフォルト』
（モーション）が、同じ性質のものなのに別の場所にあって分かりにくい」という指摘があり、統合した。
- `歌詞デコ`（lyricDeco）・`字幕スタイル`（lyricStyle）のセレクトを「歌詞の全体調整」セクションから、
  タイムラインのすぐ上にある`全体のデフォルト`（defaultMotion）の並びに移動。
  「**全行の既定値：モーション／デコ／配置**」として1箇所にまとまった（IDは変更していないのでJS側の修正は不要）。
- 「歌詞の全体調整」セクションには、行の既定値という性質ではない曲全体設定
  （タイミング補正・1行の最大表示・文字送り）だけが残った。
- 既定値の置き場所を、それが効く対象（タイムライン）のすぐ上に統一したことで、
  「ここを変えれば全行に効く」という関係性が見た目でも分かりやすくなった。

### 追記：タイムライン行のレイアウトを刷新（アコーディオン型・案3+2のハイブリッド）
歌詞が2文字程度しか表示されない不具合（`.txt`の`overflow:hidden/ellipsis/nowrap`が原因）を修正した上で、
「見づらい」「矢印を押した時に何のことか分からない」というフィードバックを受け、3つのレイアウト候補を
モックアップで提示。**案3（アコーディオン）の構造＋案2（表形式）の中身**というハイブリッドで合意し実装した。

- **通常の歌詞行**を`<details>`による折りたたみ式に変更。普段は行番号・時刻・歌詞全文だけの一覧
  （歌詞シートとして読める）。クリックすると、その行だけ編集欄が展開する。
- 展開時の中身は表形式的な2列グリッド：左列「**文字演出**」（モーション／デコ／配置）、
  右列「**素材**」（背景／キャラ／位置／大きさ／動き／エフェクト）。各列に色分けした見出しラベルを付け、
  「これは文字のことかキャラのことか」が一目で分かるようにした。
  ラベル表記は指示により「演出」→「**文字演出**」に統一（タイムラインの見出し・全行の既定値欄も同様に変更）。
- 将来の一文字ずつのタイミング編集は、この展開パネルに3つ目のグループとして追加できる設計にしてある
  （行ごとに独立した展開領域を持つため、後から機能を足しても他の行に影響しない）。
- セクション見出し・間奏行（ゾーンのまとめ役）は変更なし（元々常時表示・少数なのでアコーディオン化していない）。
- ブラウザで確認：折りたたみのデフォルトは閉、クリックで開閉、展開中に選択欄を操作しても閉じない、
  Undoが正しく効く、歌詞全文が表示される、ことを確認済み。

### 追記：秒数クリックの不具合修正／青帯（セクション見出し）の項目整理
- **秒数クリックでプレビューに飛ばない不具合**：時刻バッジのクリックが`<summary>`のonclick（renderMini）と
  `<details>`のネイティブ開閉トグルを同時に引き起こしていたのが原因。時刻バッジは
  `preventDefault`/`stopPropagation`で開閉を止め「プレビューへジャンプ」専用に、歌詞テキスト部分は
  開閉専用に役割を分離した。
- **青帯（Verse/Chorus等のセクション見出し）の項目整理**：調査の結果、青帯は直下の「そのセクション最初の
  歌詞行」と**同じデータ**を指しており、背景／キャラ／位置／大きさ／動き／FXの欄が完全に重複していた
  （どちらで編集しても同じ行の同じフィールドを書き換えるだけ）。ユーザー確認の上、青帯からこれらを削除し
  「切替演出」のみに整理。代わりに「↓直下の行を開くと背景・キャラ・FXをこのセクション全体に設定できます」
  という案内を表示。間奏行（前奏/間奏/後奏・黄帯）は歌詞本文を持たず素材を置く場所がそこしかないため、
  フル項目のまま維持。ブラウザで青帯=1個、黄帯=6個のセレクトになることと、drawFrameが全区間エラーなく
  通ることを確認済み。

### 追記：青帯の案内をボタン化／黄帯に切替演出を追加／キーボードショートカット
- **「直下の行を開けない」問題**：青帯の案内が単なるテキストで、クリックしても何も起きなかった。
  ボタン化し、クリックすると直下の`<details>`行を実際に開いて中央にスクロールするようにした。
- **黄帯（前奏/間奏/後奏）に切替演出が無かった問題**：`sectionBoundaries()`が間奏行を除外していたため、
  そもそも間奏の`trans`を設定してもセクション切替演出が発火しない作りだった。間奏行も境界として含めるよう
  修正し、黄帯にも青帯と同じ「切替演出」セレクトを追加。
- **編集中のキーボードショートカット**（動画編集ソフトの慣例に合わせて割り当て）：
  - `Space`：再生/一時停止（②編集画面は仮合成プレビュー、③は本プレビューが対象）
  - `←` `→`：5秒送り／`Shift+←` `Shift+→`：1秒送り
  - `Home`：曲の先頭へ
  - `Ctrl+Z` / `Ctrl+Shift+Z`：元に戻す/やり直す（既存）
  ②③それぞれの操作パネル下に一覧を明記。テキスト入力欄・選択欄にフォーカスがある間は発火しない。
  ブラウザで各キーが正しい関数を正しい引数で呼ぶことを確認済み。

### 追記：再生中ジャンプ不具合／青黄帯の時刻表示／セクション一括設定／Homeキー変更
- **再生中にタイムラインを押すと正しく飛ばない不具合**：`renderMini(t)`は`audio.currentTime`を変更せず
  一時的にその時刻のフレームを描くだけだった。仮合成プレビュー再生中は`requestAnimationFrame`ループが
  `audio.currentTime`を使って毎フレーム描き直すため、クリック直後の1フレームだけ正しい絵が出て
  すぐ元の再生位置に戻る（＝「エフェクトだけ出て飛ばない」）状態になっていた。
  `jumpMini(t)`という共通関数を新設し、`audio.currentTime`を実際に書き換えるよう統一
  （再生中でなければその場で`renderMini`も呼ぶ）。行の時刻クリック・見出しのサムネ/時刻クリックを
  すべてこれに置き換えた。実際にaudio.currentTimeが正しく更新されることを確認済み。
- **青帯・黄帯にも時刻を表示してタップでジャンプできるように**：歌詞行の時刻バッジと同じ見た目・挙動の
  時刻表示を見出し行にも追加。
- **青帯の「セクション一括設定」パネル**：単なる「直下の行を開く」ボタンをやめ、見出し直下に
  文字演出（モーション/デコ/配置）＋素材（背景/キャラ/位置/大きさ/動き/FX）をまとめて選べる展開パネルを新設。
  「適用」を押すと、選んだ内容を**そのセクション内の全行に上書き**する（ユーザー確認の上でこの挙動に決定）。
  すでに行ごとに個別編集された行がセクション内にある場合は、上書き前に確認ダイアログを出す。
  行ごとの細かい編集とは別物であることが伝わるよう、パネル内に説明文を明記。
  黄帯（間奏行）も同じ見た目の展開パネルに統一したが、間奏行は歌詞本文を持たない1行だけの存在なので、
  ここは各行に直接バインドする通常の素材編集（適用ボタンや上書き確認は不要）のまま。
  ブラウザで、個別編集がある場合は確認ダイアログが出ること／無い場合は出ないこと／適用でセクション内の
  全行が正しく上書きされることを確認済み。
- **Homeキーが分かりにくい問題**：物理的に見つけにくいというフィードバックを受け、`0`キー（テンキー含む）を
  曲頭へジャンプする主なショートカットとして追加（表示テキストも`Home`→`0`に変更）。Homeキー自体も
  そのまま使えるようにしている。

## 11. MV文法（Music Video Grammar）— おまかせMVを「ランダム」から「文法」へ

### 11-0. なぜ必要か
現状のおまかせMVは、演出をハッシュ乱数で選んでいる。設定項目が増えるほど、
**選択肢の数だけ「破綻する組み合わせ」も増える**ため、このままでは機能追加が品質低下に直結する。
必要なのは選択肢を増やすことではなく、**選ばせない仕組み**＝文法である。

### 11-1. テーマと文法の役割分担（重要な前提）
この2つは直交する概念で、両方揃って初めて機能する。

| | 役割 | 決めること | 例 |
|---|---|---|---|
| **テーマ**（実装済み） | 語彙 | **何を**使うか | ネオンなら発光ON・青紫系・円ワイプ系 |
| **MV文法**（本章） | 構文 | **いつ・どの強さで**使うか | 落ちサビは最小、ラスサビは最大 |

同じ文法＋違うテーマ ＝ 見た目は違うが、どちらも構成が破綻しない。これが目指す状態。

### 11-2. 三層構造

```
[第1層] セクションタグ  →  役割(role)
        [Verse 1] [Pre-Chorus] [Bridge / 落ちサビ] [Last Chorus] …
                        ↓
[第2層] 役割  →  熱量(energy 0.0〜1.0) ＋ 曲全体の起伏カーブ
                        ↓
[第3層] 熱量  →  全パラメータを導出
        文字サイズ / モーション / デコ密度 / エフェクト / キャラサイズ・動き /
        切替演出の派手さ / パンチズーム深さ …
```

**設定項目がいくつ増えても、おまかせが判断するのは「熱量」ひとつだけ**にする。これが破綻を防ぐ骨格。

### 11-3. 第1層：セクションタグ → 役割（`AI Bubble`の実タグに準拠）

| タグ例 | 役割 | 熱量 | 意図 |
|---|---|---|---|
| `Intro` | 導入 | 0.20 | 世界観の提示。静か |
| `Instrumental` / `（間奏）` | 息継ぎ | 0.30 | 歌詞なし。映像で見せる |
| `Verse 1` | 抑制 | 0.35 | 抑えて始める |
| `Verse 2` | 抑制＋ | 0.45 | 1番より少しだけ厚く（＝進行感） |
| `Pre-Chorus` | 助走 | 0.60 | 上昇。畳みかける |
| `Pre-Chorus2` | 助走＋ | 0.68 | |
| `Chorus` | 解放 | 0.85 | 最初の爆発 |
| `Chorus2` | 解放＋ | 0.90 | 1回目を必ず超える |
| `Bridge / 落ちサビ` | **落差** | **0.15** | ★意図的に全曲の最小値まで落とす |
| `Last Chorus` | **最大** | **1.00** | ★全曲の頂点。ここが一番派手 |
| `Outro` | 余韻 | 0.25 | 静かに終わる |

**この表の肝は「単調増加させない」こと。** 落ちサビで一度どん底まで落とすからラスサビが効く。
これは人間の編集者が必ずやっている操作で、ランダムでは絶対に生まれない。

未知のタグ（`Hook`, `Drop`, `C melo` 等）は、キーワード部分一致で最も近い役割へフォールバックし、
どれにも当たらなければ前後のセクションの熱量の中間値を取る。

### 11-4. 第2層：音から熱量を補正する（タグに頼りきらない）
`autoBPM()`が既に音声をデコードしているので、**セクション区間ごとのRMS音量を測るのは追加コストほぼゼロ**。
タグ由来の熱量に実際の音量を加味して補正すれば、「落ちサビと書いてあるが実は盛り上がっている」ような
曲でも破綻しない。タグ7割・実測3割程度のブレンドを想定。

### 11-5. 第3層：熱量 → パラメータ導出（対応表）

| パラメータ | 導出 |
|---|---|
| 文字サイズ倍率 | `0.90 + e*0.35` |
| モーション | `e<0.30`→ふわっと/じわズーム ・ `0.30〜0.65`→ポップイン/スローイン ・ `>0.65`→ビートバウンス/文字弾け |
| デコ密度 | `e` に比例（0＝出さない、1＝ほぼ毎行） |
| エフェクト | `e<0.35`→なし ・ `0.35〜0.70`→しゃぼん玉等の弱いもの ・ `>0.70`→キラキラ/フレア |
| キャラサイズ | `e<0.40`→小 ・ `〜0.75`→中 ・ `>0.75`→大 |
| キャラの動き | `e<0.30`→静止 ・ `〜0.70`→ふわふわ ・ `>0.70`→跳ねる |
| パンチズーム深さ | `e*0.06`（サビ以外も熱量が高ければ薄くかかる） |
| **切替演出の派手さ** | **前セクションとの熱量差 `Δe` に比例**（下記） |

**★切替演出は「絶対的な熱量」ではなく「熱量の変化量」で選ぶ。**
落ちサビ(0.15) → ラスサビ(1.00) の `Δe=0.85` が全曲最大なので、**自動的に一番派手な演出がそこに入る**。
逆に Verse 1 → Verse 2 のような小さい変化には、控えめな切替しか入らない。
これが「ここぞで決まる」感覚を機械的に作り出す仕組みで、乱数配置との差が最も出る部分。
テーマの`transPool`は「派手さ順に並べた配列」として持ち直し、`Δe`で配列内の位置を決める。

### 11-6. 文法ルール（第3層の上に重ねる制約）

**A. 反復（同じものは同じ顔で返ってくる）**
同じ役割のセクションは**同じ乱数シード**を使い、同じ系統の見た目にする。
Chorus と Chorus2 と Last Chorus は「同じ服装で、より成長した姿」になるべきで、別人になってはいけない。
現状はハッシュに境界インデックスを使っているため毎回別物になり得る。ここを役割ベースに変える。

**B. フックの signature 化**
曲名（クレジットの`【曲名】`）に含まれる語を歌詞行が含む場合、その行は**毎回同じ特別扱い**にする。
※現状のコードは `/bubble/i` が**ベタ書き**されており、この曲でしか機能しない。曲名から動的に取るよう一般化する。

**C. 一度に変えるのは1つだけ**
セクション内では背景・キャラ・エフェクトを同時に変えない。同時変更が許されるのは役割が切り替わる境界のみ。

**D. 密度の呼吸**
エフェクトが鳴りっぱなしだと、鳴っていないのと同じになる。熱量の低い区間は**実際に何も出さない**。

**E. 可読性は美観に優先（ハードフロア）**
背景の代表色に対して文字のコントラストが不足する場合、テーマの指定色より可読性を優先して自動調整する。

### 11-7. タブーリスト（生成後の破綻チェック）
おまかせで組み立てた後に検査して自動修正する工程を挟む。
**新機能を足すたびに増やすのが「選択肢」ではなく「禁止ルール」になるため、機能が増えるほど賢くなる。**

- 派手な切替演出が2連続で出ている
- 明るい背景に明るい文字（コントラスト比が閾値未満）
- 大サイズのキャラが中央＋かぶせ字幕（顔が完全に潰れる）
- 同じ背景が3セクション以上連続
- 熱量が単調増加のまま落ちサビが存在しない（＝山場が作れていない）
- デコが連続10行以上出ずっぱり

### 11-8. GPTの活用方法（※アプリの「通信ゼロ」は壊さない）
フッターに掲げている**サーバー不要・通信ゼロ**はこのアプリの資産なので、実行時にAPIを叩く実装はしない。
GPTは**設計時**と**手動の橋渡し**の2箇所で使う。

1. **設計時（オフライン）**：11-3の熱量表、11-7のタブーリスト、テーマごとの語彙選定を、
   GPTと壁打ちして精度を上げる。成果物は静的な定数テーブルとしてHTMLに焼き込む。通信は発生しない。
2. **手動の橋渡し（任意・上級者向け）**：歌詞と曲の雰囲気をGPTに渡し、
   **「演出プランJSON」を出力させて①から読み込む**。既存のタイミングJSON読み込みと同じ導線に乗るので、
   アプリ側の改修はスキーマ追加のみで済み、オフライン性も保たれる。
   「この曲は切なめなので寒色に」といった、曲ごとの解釈を入れたい場合の逃げ道として用意する。
3. **参考動画の分析**：動画そのものは解析できないが、**静止画（スクリーンショット）は解析可能**。
   好きなリリックビデオのフレームを集めて、文字占有率・余白・色数・キャラと文字の重なり方などを

4. **ユーザー自身の手直しを教師データにする**：「おまかせ直後の状態」と「完成時の状態」の差分は、
   あいさん自身の好みそのもの。プロジェクトJSONが両方あれば分析でき、既定値の調整に使える。

## 12. エフェクトの質感向上（「チープに見える」問題への対応）

ユーザーから「エフェクトがチープすぎる」との指摘があり、コードを調査した結果、原因を4点に整理した
（`globalCompositeOperation`と`ctx.filter`が実装中に一度も使われていないことをコードで確認済み）。

1. **加算合成が使われていない**：キラキラ・フレア・しゃぼん玉等の光り物が通常合成（`source-over`）で
   描かれており、光が重なっても明るくならず「半透明のシール」に見えていた。
2. **奥行きがない**：粒のサイズと速度が独立した乱数で、連動していない。
3. **レイヤーが1枚**：エフェクトが全部キャラ・文字の背後に描かれ、画面が「奥・中・手前」に分離していない。
4. **仕上げ層がない**：背景・キャラ・文字・エフェクトが別々に描かれたまま合成されておらず、
   ビネットや色被りなどの「1枚の絵にまとめる」処理が無い。

このうち**1（加算合成）だけ**を先行実装し、ブラウザ上でON/OFFを切り替えて見比べられるようにした
（見た目の変化はこちらの解像度の低いブラウザ環境では判断できないため、ユーザー自身が実際に見て
判断する前提で、比較しやすいUIを用意する方針とした）。

### 12-1. 実装したもの（加算合成トグル）
- `state.fxBlend`（true/false）を新設。②パネルに「✨ エフェクトを光らせる（加算合成）」チェックボックスを
  常設し、ON/OFFの状態を文言でも表示（「今：ON（光が重なるほど明るくなる）」/「今：OFF（従来通り）」）。
- `withAdditive(fn)`という共通ラッパーを新設。ON時は`ctx.save()`→`globalCompositeOperation="lighter"`→
  描画→`ctx.restore()`で囲み、OFF時は素通しにする。
- 対象：`drawBubbleSet()`（🫧しゃぼん玉・背景の泡）／`flare`（🌟フレア）／`sparkle`（✨キラキラ）／
  `drawSparks()`（文字弾けの飛び散り）／`popFx`（丸ぽんっ）。桜の花びらは光ではないので対象外。
- gatherSettings/applySettingsで永続化。
- ブラウザで確認：ON中は描画の瞬間だけ`globalCompositeOperation`が`lighter`になり、描画後は必ず
  `source-over`に戻る（文字やキャラに合成モードが漏れない）ことを確認済み。

### 12-2. 未着手（次回・ユーザーの目視確認を待って判断）

## 13. 構想の練り直し（2026-07-26）

F2の途中で一旦手を止め、全体の方向性を作り直した。きっかけは加算合成（発光）の導入で
「クオリティが目に見えて上がった」という体験。同じ効き方をする施策を優先的に探す。

### 13-1. ゴールの再定義
> 再現性のある、クオリティの高いリリックビデオを、何本も簡単に作れるようになりたい。
> 完成度は8割でよい。残り2割は人間がこだわる余地として意図的に残す。

- **AIが全部やるソフトではない**。8割を自動で出し、2割を人間が詰められる形にする。
- ただし「最低限のセンス」は自動側に必要。そこをMV文法として言語化する。

### 13-2. 参考MVの分析（スクショから抽出した技法の一般化）
ユーザー提供のスクショ（アイドルのコール動画系／実写＋手描き装飾系／イラスト＋
タイポグラフィ系）を分析。**丸パクリではなく技法として一般化**すると5要素に分解できた。

| 技法 | 一般化した内容 |
|---|---|
| 手描き風デコ素材 | 透過PNGのステッカーを画面の隅・被写体の周りに散らす |
| **ボイリング（微振動）** | 素材を常時わずかに揺らす／回す。**手描き感の最大の要因**。静止すると途端に安っぽくなる |
| 一文字ごとのタイポグラフィ | 文字ごとにサイズ・回転・ベースラインをずらす。キーワードだけ拡大＋別色 |
| 文字の質感 | ドット網点（ハーフトーン）、極太フチ、二重フチ |
| 場面転換の「物」化 | 図形ワイプではなく、ノートのページめくり・リボンが横切る等 |

→ **「センス」の大部分は「素材の質 × 配置ルール × 微振動」に分解できる**。
　ここが再現性の鍵であり、プログラムで扱える。

### 13-3. 3本の柱
- **柱A：ステッカーパック・システム**（素材を活かす中核）
- **柱B：一文字タイポグラフィ・エンジン**
- **柱C：切替演出の作り直し**

### 13-4. 素材の2階層モデル（柱Aの設計・合意済み）
| 種別 | 保存先 | 対象 | 理由 |
|---|---|---|---|
| **ライブラリ素材** | IndexedDB（永続） | デコ素材、フォント | 一度入れたら全プロジェクトで使い回す |
| **プロジェクト素材** | JSON内に埋め込み | キャラ、その曲専用の背景 | 使い捨て。他PCでも開ける |

- 土台は既に存在する：`fontDB()`が`fonts`と**`assets`**の2ストアを作っており、
  `saveAsset()`/`deleteAsset()`も実装済み。ここにデコ素材を載せる。
- **フォント読み込みは既に実装済みだった**（`🔤 フォントを追加` ttf/otf/woff2・IndexedDB永続）。
  当初「これから作る」と誤って提案したが、既存機能である。
- **グリーンバックPNGの取り込みに対応する**：Geminiで透過PNGを作るのが難しいため、
  取り込み時にクロマキー除去（緑を透明化）を行い、**透過状態にしてから**IndexedDBに保存する。
  変換は初回1回だけ。しきい値スライダーで調整可。緑系の素材が消える問題への逃げ道として
  マゼンタ背景も選べるようにする。
- **内蔵プリセットパック**：コードで描画する手描き風デコ（音符・ハート・ぐるぐる・キラキラ・
  集中線等）を同梱する。画像ファイル不要＝容量ゼロ＝「通信ゼロ・サーバー不要」を維持できる。

### 13-5. 柱Cの真因（コード調査で確定）
「切替演出が不自然。背景がベタ塗りで別の色になる」というフィードバックの原因を特定した。

- `drawSectionFx()`内の`baseCover()`が、切替の中盤で
  **画面全体を`TRANS_COLORS`（ピンク/水色/黄/緑/紫）のベタ塗りで完全に覆っている**。
- この色は**実際の背景画像とも曲の世界観とも無関係な固定パレット**。
- つまり原因は演出の種類ではなく**設計そのもの**。「モノ化」した演出を追加しても、
  `baseCover`が残る限り同じ不自然さが出る。

**正しい直し方**：「べた塗りで隠す→開けたら次の背景」ではなく、
**「次の背景そのものを、形で切り抜きながら見せる」**方式へ作り替える。
関係ない色が一切出なくなる。既存10種の形（丸・ダイヤ・市松…）はそのまま流用できるため、
作り直しではなく**描画方式の差し替え**で済む。

### 13-6. 「AIのセンス・学習」についての整理（正直な限界と代替）
- Claudeをユーザーのデータで**ファインチューニングすることはできない**。
- 代替となる実用的な手段が2つあり、これで足りる：
  1. **ルール化**：好きなMVの技法を文法ルールとして言語化しコードに焼く（既存のMV文法の延長）
  2. **画像レビューのループ**：Claudeは画像を読めるので、「アプリの出力スクショ」と
     「理想のMVのスクショ」を並べて渡せば、差分を指摘して文法ルールを改善できる。
     これが実質的な学習ループになる。
- **GPTの役割**：静止画では取れない**時間軸の情報**（装飾の出現タイミング・持続時間・密度の
  変化・サビ前の溜め・繰り返しの度合い）を動画から抽出してもらう。
  依頼文は `GPT-依頼書.md` に用意済み。数値で返すことを必須にしてある。
- **Geminiの役割**：世界観に合う素材（デコ素材・背景）の画像生成。

### 13-7. 役割分担

### 14-1. 出典と信頼度（重要）

### 14-2. 相互検証：既存の熱量カーブとの一致

| イントロ | 1.00 | 1 | 一致 |
| Aメロ | 1.75 | 1.5 | 近い |

### 14-3. 相互検証：切替演出の不自然さの裏付け

| 項目 | 一般的なMV | v12の現状 | 差 |
|---|---|---|---|
| 転換の所要時間 | 0.15〜0.35秒（激しい曲は0.05秒） | `DUR=0.85`秒 | 2.5〜5倍遅い |

→ 不自然さは**①遅すぎる ②毎回起きる ③色が無関係**の複合。
　13-5の「べた塗り撤廃」に加え、**単に速くするだけでも大きく改善する**（低コストで効く）。

### 14-4. 採用する構成：見た目と時間軸の分離
GPTの提案を採用。同じ素材でテンポ感だけ変える／同じテンポ感で別テーマ、が可能になる。

- **見た目側**：Theme（配色・フォント）／Object（デコ素材）
- **時間軸側**：
  - **Rhythm**：拍・小節・歌詞タイミングへの同期ルール
  - **Intensity**：セクションごとの演出密度の倍率
  - **Lifetime**：各オブジェクトの寿命・出現/退場の速度

### 14-5. 数値仕様（v1のデフォルト値）

**Lifetime（寿命・速度）**
| 種別 | 寿命 |
|---|---|
| 小さいデコ（ハート等） | 0.5〜1.5秒 |
| 手描き線 | 1〜3秒 |
| ステッカー | 2〜6秒 |
| 背景フレーム | 5〜20秒 |
- 出現：0.08〜0.18秒（かわいい系は0.15〜0.30秒）
- 退場：0.10〜0.25秒。**フェードではなく「縮小＋透明化」が多い**
- 原則：**重要でない装飾ほど短命**

**微振動（ボイリング）＝手描き感の肝**
- 周期 2〜4秒／振幅 2〜5%／回転 ±0.5〜1°
- **完全静止は避ける**

**Intensity（密度）**
- 同時表示数：静かな場面 2〜6個／通常 8〜15個／サビ 15〜35個／コール動画系 40〜80個
- セクション倍率（イントロ=1）：Aメロ1.5／Bメロ2／サビ3〜4／間奏2／落ちサビ0.8／ラスサビ5

**歌詞テキスト**
- 1フレーズ 2〜5秒表示。次の歌詞と0.2〜0.5秒重なるのが主流（完全に消えてから次は少数派）
- 一文字ずつ出す割合：ボカロ系70%／アイドル40%／実写30%。文字間遅延 0.02〜0.06秒
- 強調単語：1行あたり平均0.6〜0.9語（サビは1.2語）。スケール120〜160%
- 位置：固定40%／移動60%。移動は**ランダムではなく左右・上下・対角を循環**

**Rhythm（同期）**
- 拍同期率 約80%。4分・8分で切る。16分はアクセントのみ
- デコ=8分／文字=4分／場面転換=小節頭 が最頻

**曲構造**
- サビ直前：0.1〜0.3秒の静止／0.05秒の白フラッシュ／0.2秒の余白 のいずれか
- 落ちサビ：演出量を通常の40〜60%に。装飾半減・揺れ弱め・文字ゆっくり
- ラスサビ：通常サビの1.5〜2倍。装飾1.5倍・速度1.2倍・カメラ揺れ追加
- 1番→2番：完全コピー10%／少し変える70%／全変更20%
  → **「20〜40%だけ変更」を既定とする**（既存の反復ルールと整合）

### 14-6. 自動生成ルール（実装対象）
1. 新しい歌詞が出るたび30〜70%の確率で新デコを生成

4. 全デコに周期2〜4秒・振幅3%程度の微振動

### 14-7. 切替演出の全面改修（実装済み）
13-5・14-3で特定した真因に対応した。

- **`baseCover()`によるべた塗りを完全撤去**。`TRANS_COLORS`／`transColor()`は切替演出から消えた。
- 「べた塗りで隠して開けたら次の背景」→ **「次の背景そのものを形で切り抜いて見せる」**方式へ。
  `pickBg(境界行)`で次の背景を取得し、各図形で`clip()`してから描く。無関係な色が出る余地がない。
- **タイミングを作り直した**：`sin(p*π)`（覆って晴れる）→ 単調に開ききる`E(p)`。
  演出は**歌詞が始まる瞬間ちょうどに完了**する（`st=lineTime-DUR`）。完了時の絵＝次の背景なので継ぎ目が出ない。
- **所要時間を実測値に合わせた**：一律0.85秒 → 種類ごとに0.14〜0.30秒（`TRANS_DUR`）。
  派手なものほど速い。white=0.14（フラッシュ内でカットが入れ替わる古典的手法）。
- 図形のふちに白線（`rim()`）を足し、「手描きの切り抜き」らしさを出した。

**検証**（実データ AI Bubble_project.json）
- 全9箇所の切替で**前シーンの漏れ 0.00%**（下地を目印色で塗り、演出完了直前のピクセルを計測）
- `drawSectionFx`内に`transColor`/`TRANS_COLORS`の参照が**0件**
- 所要時間：0.20〜0.30秒（旧0.85秒）
- 0〜200秒・0.4秒刻みで`drawFrame`エラー0件

### 14-8. ステッカーへのフィードバック対応（実装済み）
- **「点々（丸3つ）」を削除**（ダサいとの指摘）。プリセットは11種になった。
- **ボイリングを作り直した**。「全然揺れて見えない」という指摘の原因は実装方針の誤りだった。
  なめらかなサイン波で揺らしていたため「ふわっと漂う」だけになっていた。
  **手描きアニメのプルプルは、毎秒8〜11コマでカクカク描き直されることで生まれる**ため、

  振幅も位置±6.5%・回転±2.9°・大きさ±3.5%へ引き上げた。
  検証：60fpsのうち約7フレーム静止→1フレームで飛ぶ挙動を確認（≒8.5コマ/秒）。

  `drawChars`を`layoutChars`（配置計算）と`drawChars`（描画）に分離。
  描画前に位置が分かるようにして、**ステッカーをキャラより後ろ**に移動した。
- **顔・主役部分の回避**を追加（`charKeepOut()`）。矩形の上半分・中央寄り（横14〜86%・縦-2〜52%）を

## 16. フィードバック対応（2026-07-27 続き）

### 16-1. 歌詞を直接編集できる場所を「①素材読み込み」の大きな欄に統合

  （`charTimes`）は失われない**ことを確認済み（検証参照）。

### 16-2. 「一文字ずつボーカルに同期」が効いていなかった不具合の修正
「ボタンを押しても一文字ずつのタイミングに合わない」という報告を調査し、
**2つの問題**が見つかった（ボタンの場所自体は②演出指定パネルのBPM設定の並びで意図通り）。

1. **fuwa/zoom/slideモーションは、そもそも`charTimes`を見ていなかった**：
   これらは「行全体が`t0`基準で一斉に出る」実装のままだったため、popin/bounce/burst以外の
   モーションを選んでいる限り、ボーカル同期を実行しても**見た目に一切変化が出なかった**。
   これが今回の症状の直接原因。fuwa・zoomは`t0`基準から`tk`（＝charTimes反映後の
   文字ごとの時刻）基準に変更し、1文字ずつ順番に現れるようにした。slideは「行全体が
   ひとつの塊として枠外から流れ込む」という演出の性質上、1文字ずつに分解すると
   逆に破綻するため、意図的に対象外のままとした。
2. **「文字送り」欄の表示名が誤解を招いていた**：既定値の選択肢が「歌詞になるべく合わせる
   （1文字ずつシンクロ）」と表示されており、あたかもこれ自体がボーカル同期であるかのように
   読めたが、実際は単なる均等割り（行の表示時間を文字数で均等分配）で、音声解析とは無関係
   だった。「1文字ずつ均等に出す」に改称し、「🎤ボーカル同期を実行した行はそちらが優先され、
   この設定は未解析の行にのみ使われるフォールバックである」旨を明記した。
   タイミング補正・1行の最大表示は現状維持（ユーザー確認済み・引き続き必要）。

### 16-3. ステッカーのボイリング量：GPT追加分析の数値をそのまま反映
14章追記のGPT回答（装飾別の推奨ボイリング量・更新頻度の表）を`STK_BOIL`として実装した。
一律だった振幅（位置±5.5%・角度±2.6°・大きさ±3%＝「2〜3倍揺れ過ぎ」との指摘）を廃止し、
装飾の種類ごとに個別の値・更新頻度（拍数）を持たせた。集中線・手描き線は角度/大きさの
振動を0にし、位置のみわずかに動かす。音符は最も大きく揺れ、毎拍更新。

**検証**：全11種の装飾でボイリング計算式を単体検証し、GPTの表通りの大小関係
（音符4.78% > ハート3.82% > キラキラ2.87% > 集中線1.43%、Rに対する割合）を確認。
全種類でdrawFrameエラー0件。

BPMによる更新頻度の調整（GPT回答の「150〜200bpmは一部のみ毎拍」）は**今回は見送り**。
現状の固定値で問題が出た場合に対応する。

### 16-4. 歌詞と歌の同期精度を改善（文字単位）
「同期の精度がかなり低い」というフィードバックを受けて原因を調べ、3つの欠陥を特定した。

1. **全帯域の音量差分をそのまま使っていた** → キック/ベース/スネアが支配的で、
   肝心のボーカルの立ち上がりが埋もれていた。
2. **強い順にn個拾って時刻順に並べるだけだった** → 1音節の中に複数ピークが立つと
   そこで枠を使い切り、後半の文字が全部同じ時刻に潰れていた。
3. **日本語を1文字＝1音として扱っていた** → 「しゃ」「きょ」「っ」「ー」に個別の
   タイミングを割り当てようとして必ずズレていた。

**対策**
- 声の帯域（およそ300〜3400Hz）だけを1極フィルタのバンドパスで通してから包絡線を取る。
  ステレオなら中央成分(L+R)/2を使う（ボーカルは中央定位が多いため）。
- ピークは**最小間隔0.085秒**を守って選ぶ（1音節に1個まで）。
- 日本語を**モーラ（拍）単位**にまとめてから割り当てる（小書き・長音・記号・空白は前の文字に吸収）。
  同じモーラ内の文字は同時に出す。
- 割り当ては貪欲法をやめ、**動的計画法**で順序を保ったまま全体の誤差が最小になる組を選ぶ。
- 解析窓の終端を「次の行の開始時刻」に変更（従来は`maxHold`で切られ、隣の行に食い込むことがあった）。

**検証**（実データ AI Bubble_project.json + AI Bubble_mp3.mp3、実音声）
- 旧実装：単調増加の応急処置が**479箇所中148箇所（30.9%）で発動**＝それだけ文字が
  同じ時刻に潰れていた（＝ユーザーが感じた「精度が低い」の正体）
- 新実装：**モーラ外での潰れ0件**。同時刻になっている72ペアはすべてモーラ内
  （「ずっ」「まっ」など）で、これは意図した正しい挙動であることを個別に照合して確認
- 37行を0.87秒で解析。全モーションでdrawFrameエラー0件、決定論性を維持

### 16-5. 「歌詞テキストから全自動でタイミング生成」は実装したが**出荷を見送った**
タップ打ち込みを不要にしたいという要望に対し、声の帯域の包絡線から「歌っている区間」を
検出して歌詞を順番に割り当てる方式を実装し、実データで計測した。

**結果：使いものにならなかったため撤去した。**
- 37行に対し検出できた区間は3箇所（条件を緩めても13箇所）
- **誤差300ms以内に入った行は0/37**、誤差中央値は43秒
- 原因：**伴奏も声と同じ帯域（300〜3400Hz）を占めるため、音量だけでは
  「歌っている区間」と「間奏」を分離できない**。閾値を超えたまま曲全体が1区間に繋がってしまう。

計測せずに「下書きとして使えます」と出していたら、ユーザーの時間を大きく損なうところだった。
**壊れた機能は出さない**方針を優先した。

### 16-6. 代わりに「行のタイミングを歌に吸着」を実装（確実に効く方式）
全自動が無理でも、精度は上げられる。**人が与えた大まかな位置（タップ／既存JSON）は信用し、
アルゴリズムは「その近くにある本当の歌い出し」へ寄せるだけに徹する**方式に変更した。

- ①パネルに **「🎯 行のタイミングを歌に吸着」** を追加。各行を**±0.30秒の範囲だけ**探索し、
  最も強いボーカルの立ち上がりへスナップする。範囲を狭く固定しているので暴走しない。
- 行頭が動いた行は`charTimes`を破棄し、文字単位の同期をやり直せるようにした。
- タップ打ち込みの直後に1回押す運用を想定（手押しの早すぎ・遅すぎを機械が補正する）。

**検証**：実データで35/37行が吸着、平均162ms移動、最大291ms（設定範囲±300ms内に収まる）、
行の順序（単調増加）も維持。範囲外へ飛んだ行0件。

**全自動化に必要なもの（今後の選択肢）**
- **ボーカル分離**（Spleeter/Demucs相当）：伴奏を除去できれば区間検出は一気に容易になるが、
  モデルが数十MB〜あり「単一HTML・通信ゼロ」の原則と衝突する。
- **音声認識（ASR）**：Whisper等。同様にモデル配布が必要。Web Speech APIはファイル音声に使えない。
- → いずれも現在の設計方針（サーバー不要・通信ゼロ・単一ファイル）を変える判断が要る。
  当面は「タップ＋吸着」で精度を稼ぐのが現実的、というのが今回の結論。

### 16-7. その他のフィードバック対応
- **セクション読み取り欄を横にも拡大**：`width:min(96vw,2200px)`で親コンテナ（1120px）を
  はみ出して画面幅いっぱいまで使えるようにした。
- **「丸が3つ連なった車みたいな形」を削除**：前回消したのは`dots`（点々）だったが、
  ユーザーが指していたのは`puff`（もこもこ＝3つの円を横に並べた形）だった。
  プール・ボイリング表・描画関数から完全に撤去（プリセットは10種になった）。
- **ステッカーの揺れが小さすぎて見えない問題**：GPTの推奨値は実際のMVの数値だが、
  プレビューの表示サイズでは動いて見えなかった。**種類ごとの比率は保ったまま
  全体を掛け算で強められる倍率（`state.stickerBoil`、既定3、0〜8）**をUIに追加した。
  検証：×1→×3で移動量がちょうど3.00倍になり、種類ごとの大小関係（音符>ハート>集中線）も維持。

## 17. フィードバック対応（2026-07-27 続き）

### 17-1. セクション読み取り欄の幅を固定
ブラウザ幅に連動して伸び縮みしていた（`96vw`指定が原因）。`width:1400px;
max-width:calc(100vw - 40px);` に変更し、通常のPC画面では常に同じ幅（パネル幅の
約1.3倍）で安定するようにした。ウィンドウが1400px未満のときだけ追従して縮む。

### 17-2. セクション読み取り／歌詞反映を自動化
「セクションを読み取る／歌詞を反映」ボタンを削除し、`sectionText`欄への入力が
**0.5秒止まったら自動で`importSections()`を実行**するようにした（デバウンス）。
処理内容は文字列の突き合わせのみで数千回比較しても1ミリ秒未満のため、負荷は問題にならない。
変換中の未確定文字列で誤爆しないよう、打鍵のたびではなく「止まったら」実行する方式にした。

### 17-3. ステッカーの揺れをさらに強化
既定値を3→**6**、上限を8→**20**に引き上げた。また、小さいステッカーは
`R*bo.pos`自体が小さく、倍率をかけても絶対量として動いて見えない問題があったため、
**画面高さの0.4%を下限**とする床（フロア）を追加した（`bm`に応じて0→1の間で
比例的に効き、`bm=0`では完全に静止したままにできる）。

### 17-4. 「単一HTML・通信ゼロ」の意味を説明
ユーザーからの質問に回答：永久に動く／曲が外部に出ない／オフラインで動く／
バックアップがファイル1個／費用と障害がゼロ、という利点がある。代償は重いAIモデル
（ボーカル分離・音声認識）が使えないことのみで、これは16章で実際にぶつかった制約。

### 17-5. ボーカルのみの音源を解析専用の材料として追加
「ボーカルのみのデータがある」との情報を受け、①パネルに
**「🎤 ボーカルのみの音源（任意・解析用）」** を追加した。

- **再生には一切使わない**。歌詞タイミングの解析（`decodedAudioBuffer()`）だけがこれを使う。
  `vocalBlob||audioBlob`の優先順で選ぶため、無ければ従来通りミックス音源で解析する
  （後方互換）。
- IndexedDBの`assets`ストアに`kind:"vocal"`として永続化。フォント・背景・キャラと同じ
  「一度読み込めば次回も使える」ライブラリ素材の枠組みに乗せた。
- 16-5で判明した「伴奏も声と同じ帯域を占めるため分離できない」という制約を、
  ソフト内の処理ではなく**素材の時点で解決する**アプローチ。これなら通信ゼロ・
  単一HTMLの原則を一切崩さずに精度を上げられる。
- **全自動タイミング生成（16-5で撤去した機能）の復活可否は未検証**。ボーカル単体の
  音源であれば「歌っている区間」と「間奏」の分離が原理的に成立しやすくなるはずだが、
  実際の分離音源データが手元にないと計測できない。ユーザーが音源を用意でき次第、
  16-5と同じ方法（誤差300ms以内の行数・誤差中央値）で計測し、実用に足る精度が
  出るかを判断してから実装の可否を決める。

**検証**：`decodedAudioBuffer()`が`vocalFile`欄に読み込んだファイルを優先して解析に
使うことを確認（配線のみ。実際の分離音源での精度測定は未実施＝上記の理由）。

### 17-6. GPTへの新しい依頼：歌詞キーワード→モチーフ対応表
現在のMV文法は「いつ・どれだけ」（熱量ベースの密度）は決められるが、「何を出すか」は
完全ランダムのまま。この空白を埋めるため、GPTに「歌詞のキーワード分類→推奨モチーフ・
推奨色・推奨の動き」の対応表を依頼した（`GPT-依頼書.md`に追記）。20分類以上、
特定作品の模倣ではなく複数作品に共通する一般的傾向として依頼。

## 18. 実装フェーズ（2026-07-27 続き）

### 18-1. セクション読み取り欄の幅を完全固定
17-1の修正が`max-width:calc(100vw-40px)`にvwを残していたため、依然ブラウザ幅に
追従していた。**vwを完全に排除**し、`width:1200px`固定＋外側に`overflow-x:auto`の
ラッパーを追加する方式に変更。狭い画面では横スクロールで対応し、広い画面では常に
同じ大きさで安定する。

### 18-2. ステッカーの揺れ方を「統一」できるようにした
「揺れ幅・頻度が種類ごとにバラバラで気になる」という指摘に対応。セル画（手描きアニメ）は
画面全体を同じタイミングで一斉に描き直すため、**本来は全ステッカーの震え方が揃っているのが
自然**という判断に至った。GPTの表は「1個ずつの理想値」としては正しいが、画面全体で見た
一体感という観点が欠けていた。「揺れ方を統一」チェックボックス（既定ON）を追加し、
統一時は全種類が同じ振幅・同じ頻度（`STK_BOIL_UNIFIED`）で揺れる。OFFにすれば
従来のGPT表（種類ごとに異なる値）に戻り、直接見比べられる。

### 18-3. ボーカル単体音源での精度計測（実データ：AI Bubble (Lead Vocal).mp3）
ユーザーから分離済みボーカル音源が提供されたため、実際に計測した。

**既存機能（🎯行の吸着／🎤文字単位の同期）への効果**
- 行の吸着：ミックス音源では35/37移動・平均162ms → ボーカル単体では**36/37移動・平均126ms**
  とわずかに改善。局所的な補正なので、そもそも大きな差は出にくい
- 文字単位の同期：37/37行で成功、モーラ境界外の潰れ0%は変わらず（既にバンドパス＋モーラ化で
  ほぼ飽和していたため、劇的な変化はなし）

**全自動タイミング生成（16-5で撤去した機能）の復活は依然として見送り**
- 検出できた「歌っている区間」候補は144個（歌詞37行に対して多すぎる＝1行の中の
  音節ごとに複数区間ができてしまう）
- 単純な最近傍評価での理論上限：37行中28行が誤差300ms以内（76%）
- しかし実際の割当（動的計画法で順序を保ったまま37個を選ぶ）を行うと、
  誤差300ms以内は**37行中わずか4行**、誤差中央値2.86秒まで悪化
- 原因はミックスとの分離問題ではなく、**間奏などの無音区間により行間の間隔が
  不均一**なため、均等割りを仮定した割当アルゴリズムが機能しないこと。
  ボーカルを分離しても「どの候補が新しい行の先頭か」を判定する手がかりが
  根本的に不足している
- 結論：**ボーカル単体音源があっても全自動化は実用に届かない**。今回も撤去のまま。
  タップ＋🎯吸着という現在の運用を継続する

### 18-4. 歌詞キーワード→モチーフ辞書を実装（GPTの30分類）
GPT提案の「NLP→SemanticCategory→Object辞典」を、キーワード辞書によるスコアリングで
実装した（本格的なNLPではないが、通信ゼロ・単一HTMLの原則を崩さずに済む）。

- `LYRIC_CATEGORIES`：30カテゴリ、各々にキーワード配列・対応モチーフ名・
  内蔵ベクター形状へのフォールバック・推奨色を持たせた
- `categoryScores(text)`：行のテキストに対し辞書マッチでスコア付け
- `categoryByLine()`/`categoryAt(t)`：行ごとに主カテゴリ・副カテゴリをキャッシュ
  （`energyByLine`と同じキャッシュ設計。行編集時に`invalidateCategoryCache()`で破棄）
- 該当キーワードが無い行は**従来の熱量ベースのランダム選択にフォールバック**
  （後方互換。全曲がカテゴリだらけになる心配はない）

**検証**：実データで「宝物→takara」「光って→hikari」「青空→sora」「雨模様→ame」等、
妥当な分類がついていることを確認。

### 18-5. デコ素材の読み込み機能（ユーザー素材の受け皿）
柱Aで設計していた「ユーザーがGeminiで作った素材を読み込む」機能を実装した。

  自動で取り除きモチーフ名を抽出し、同じモチーフの複数枚をバリエーションとして束ねる

### 21-1. sectionText（歌詞テキスト欄）がJSON再読み込みで引き継がれない不具合を修正

## 24. フィードバック対応（2026-07-27 続き）

### 24-1. ステッカーの位置がゾーン内で行ごとに動いてしまう不具合を修正
23章で「セクション単位で共通化」したはずだったが、実際には**キャラ・文字を避ける
押し出し処理が毎フレーム動的**（その時点の`charKeepOut()`/`textKeepOut()`を都度
参照）だったため、行が変わって文字の位置が変わるたびに押し出され方も変わり、
結果的にステッカーの位置が動いてしまっていた。

**修正**：押し出し計算を`computeStickerBaseLayout()`の中で**セクション内の代表的な
複数時刻（開始直後・中間・終了直前）をサンプルして合成し、最終位置として一度だけ
焼き込む**方式に変更した。`drawStickers()`側は焼き込み済みの`{x,y}`をそのまま使うだけになり、
毎フレームの動的な押し出しは行わない。`textKeepOut()`は読み取り専用（`charRects`を
書き換えない）なので、サンプリングしても他の描画に影響しない。

**副作用の対応**：押し出しによってペア同士が結果的に近づくことがあったため、
キープアウト適用後にx,y空間でもう一段階の重なり緩和を追加した（325ペア中8件→3件に改善）。

**検証**：Chorus内の異なる2行で、同じセクション（ゾーン3）の全26スロットの
焼き込み位置`{x,y}`が完全一致することを確認。

### 24-2. キャラクター素材の位置・大きさを連続値で調整できるように

### 26-1. 決定の階層（GPT推奨の順序をそのまま採用）

- 適用ボタンの隣に「🔒も含めて上書き」チェックを置き、意図的に揃えたいときだけ使う
- 🔒は行ごとに手で外せる

②行ごとの位置指定は階段状に飛ぶが、カメラは時間に対して連続 ③管理する値が激減し
誤操作の余地自体が小さくなる ④静止した背景素材が生き返る（安っぽさの解消）。

**レイヤーの切り分け（確定）**
| レイヤー | カメラで動かすか | 理由 |
|---|---|---|
| 背景 | **動かす** | — |
| キャラクター | **動かす** | — |
| 歌詞 | **動かさない** | 可読性を守る |
| ステッカー | **動かさない** | 画面に貼ってあるシールなので動くと理屈が合わない |
| デコ（打点） | 動かさない | 文字に付随するため |

**技術的な注意点**：カメラでキャラが動くと、ステッカーが避ける対象（`charKeepOut`）も動く。
ステッカーの位置は既に「セクション内の複数時刻をサンプルして焼き込む」方式なので、
**そのサンプル計算にカメラ変形を含めれば対応できる**（作り直しは不要）。

## 31. バグ調査の結果（2026-07-27／原因特定済み・未修正）

### 31-1. `*キーワード*`の1文字目が強調されない ← 原因を完全に特定
**症状**：`*Fly high*`のFだけ、`*宝物*`の宝だけ強調されない。

**根本原因**：`smartRows()`が折り返しの際、**日本語の全角スペースを消している**
（`text.split(/[\s　]+/)`で分割し、`joinTok()`は英数字同士の境界にしか空白を戻さない）。
一方`emphMask`は**元のテキストの添字**で作られているため、
**スペースが消えた位置以降、添字が1つずつズレる**。

**実測（狭いスロットで折り返しを強制して再現）**
| 入力 | 期待 | 実際 | 文字数 |
|---|---|---|---|
| `青空どこまでも　*Fly high*⭐︎` | Fly high | **ly high⭐** | clean18 → positions17 |
| `寄り道だって　全部全部*宝物*♪` | 宝物 | **物♪** | clean14 → positions13 |
| `どれもぜんぶ　*わたし*` | わたし | **たし** | clean10 → positions9 |

先頭が1文字ズレて落ち、代わりに末尾の1文字が余分に強調される。全角スペースの無い行や、
折り返しが起きない行では発生しない（＝「わりとある」という報告と一致）。

**同じ原因による二次バグ（未報告だが確認）**：`drawLyric`のボーカル同期は
`line.charTimes.length===n`（n=positions.length）という条件で有効化しているため、
**スペースが消えた行では条件が成立せず、ボーカル同期が黙って無効化され均等割りに戻る**。

**修正方針**：レイアウト結果の各文字に**元テキストでの添字（srcIdx）を持たせる**。
`smartRows`/`charWrap`/`layoutLine`/`arcLayout`が文字を落としたり並べ替えても、
`positions[k].srcIdx`で元の位置を引けるようにする。`emphMask`も`charTimes`も
この`srcIdx`で参照する。添字の対応を推測に頼らない構造にするのが本質的な直し方。

### 31-2. 🔒のチェックを入れていないのにロック行が上書きされる ← 原因を特定
**根本原因**：セクション（青帯）のスライダーは、ドラッグ中のライブプレビューのために
`oninput`で**セクション先頭行に直接値を書き込んでいる**（`l[fieldKey]=+inp.value`）。
この書き込み経路に**ロックの判定が入っていない**。

「適用」ボタン側は正しくロック行を除外している。したがって**セクションの先頭行が
ロックされている場合にのみ**、スライダーを動かしただけで上書きされる。

**実測**：Chorusの先頭行と2行目の両方をロックし、チェックを外したままスライダーを
0.7へ動かした結果 → 先頭行は0.33→**0.7に変化**、2行目は0.11のまま（保護は機能）。

**修正方針**：ライブプレビューの書き込みも「ロックされていない行」に限定する。
先頭行がロックされている場合は、そのセクション内で最初のロックされていない行を
プレビュー対象にする（対象が無ければプレビュー更新のみ行い値は書かない）。

### 31-3. キャラが中央のとき、歌詞が左右に分かれず中央にかぶる ← 私の実装バグ
**GPTの回答待ちではなく、26章の実装（`applyPersonAvoidance`）の不備**。

人物が中央のとき「左余白36% / 右余白36% / 重ねる28%」を抽選し、選ばれた側のスロットを
×3、反対側を×0.15している。しかし**`center`と`bottomCenter`（＝人物に重なる位置）を
抑制していない**。さらに文字数が多い行では`BOTTOM ×2.2〜3.0`の倍率がかかるため、
`bottomCenter`の重みが side を上回ってしまう。

例：長い行＋人物中央で「左」が選ばれた場合
`left 15×3=45` / `bottomCenter 18×2.2=39.6` / `center 27` → **中央系の合計66.6が left 45を上回る**。

**修正方針**：側が選ばれたとき、**人物と重なるスロット群（人物中央なら center/bottomCenter/
topCenter）を明確に抑制する**（×0.15程度）。「重ねる」が選ばれたときだけ中央系を優遇する。
GPTの「約70%は人物を避け、30%だけ重ねる」という比率に実際に一致させる。

なお「1行を前半・後半に分けて左右に置く」機能（26-11）は**まだ未実装**であり、
上記の修正とは別件。31-3を直せば「行ごとに左右へ振り分ける」挙動にはなる。

（Pはpositions[k]）へ置き換えた。`charTimes.length`との比較も、折り返しで
減りうる`positions.length`ではなく、常に一定の`cleanText.length`基準に修正した。

**検証**：バグ報告にあった3例（`*Fly high*`／`*宝物*`／`*わたし*`）すべてで、
狭い幅に強制的に折り返させても強調範囲が完全一致することを確認。
ボーカル同期（charTimes）も同じ原因で黙って無効化されていたが、修正後は
`clean`と同じ文字数で正しく保存・参照されることを確認。0〜200秒でdrawFrameエラー0件。

**先頭行がロック済みかつ「🔒も含めて上書き」が未チェックのときは、
ライブプレビューでも書き込まないように修正**した。

**検証**：ロック済みの先頭行に対し、チェック無しでスライダーを動かしても値が

## 34. 組版バグの調査結果と改善方針（2026-07-27／原因特定済み・未修正）

### 34-1. 「青空どこまで／も／Fly high」と3行に割れる原因 ← 特定
スクリーンショットの症状を実測で再現した。**文字数の限界ではなく、アルゴリズムの不備**。

**再現結果**（`maxW`＝画面幅44%＝563px、テキスト18文字）
| フォント幅 | 「青空どこまでも」7文字の幅 | 収まるか | 結果 |
|---|---:|---|---|
| 標準フォント fs85 | 492px | ○ | **2行（正常）** |
| 幅広フォント相当 fs105 | 607px | × | **3行＋「も」1文字の孤立行** |

ユーザーは幅の広いカスタムフォントを使っているため、標準フォントでは出ない症状が出ていた。
**フォント幅に対して脆い設計**だったことが本質。

**3つの機械的な不備**
1. **`layoutLine`が3行まで許容してフォントを縮めない**
   （`if(rows.length<=3||fs<=30) break;`）。実測でfs=105のまま3行になることを確認。
2. **`smartRows`が1文字だけの孤立行を作っても何のペナルティもない**。
   トークン単位の2行分割に失敗すると`charWrap`（文字単位）に落ち、「も」が余る。
3. **配置エンジンが18文字の行に幅44%の狭いスロットを選んでいる**。
   GPTの実測では「17文字以上は58%が下部中央」なのに、33-3の修正で
   中央列を×0.15に抑制したため、長文でも下部中央が選ばれなくなった（過剰修正）。

### 34-2. 改善方針（3点セット）
**① 組版品質スコア（fitScore）を重み計算に組み込む**
候補スロットごとに実際に`smartRows`を走らせ、組版の質でペナルティを掛ける。
GPTの統計は「好み」を与えるが、**物理的な収まりがそれを上書きすべき**という考え方。
- 1行 ×1.0 ／ 2行 ×0.85 ／ 3行以上 ×0.2
- 1文字だけの孤立行がある ×0.25
- フォント縮小が必要 ×0.7
`measureText`だけなので計算は軽い。これにより「統計的に好まれ、かつ綺麗に組める」
スロットが自然に選ばれる。33-3の過剰修正も、この仕組みが入れば緩められる。

**② `layoutLine`の目標行数を2行にし、孤立行を避けるまでフォントを縮める**
現在の「3行まで許容・縮小なし」を、「2行を目標／孤立行が出たら縮小／下限あり」に変える。

**③ 1行を左右に分割（26-11）を実装する**
今回のケースの理想解はこれ。「青空どこまでも」を左、「Fly high⭐」を右に置き、
中央のキャラクターを挟む形。GPTの実測でも分割後の配置は左右が46%で最多。
**キャラが中央＋長文＋自然な分割位置がある**場合の第一候補にする。

### 34-3. 「字数的に厳しいのか」への回答
**厳しくない。** 18文字を幅44%に1行で入れるのは無理だが、2行なら標準フォントで
問題なく収まる（実測492px<563px）。3行＋孤立行になったのは組版アルゴリズムの
問題であり、左右分割すれば片側7〜10文字ずつで1行に収まる。

### 34-4. 🔒（ロック）が分かりにくい問題
**2つの不備がある。**
1. **編集しても🔒がすぐ表示されない**：`mkFieldSel`は`fullRerender`が真のとき
   （背景・キャラのみ）しか`renderLineList()`を呼ばず、`mkFieldRange`は一度も呼ばない。
   `l.locked=true`は内部的に立つが、**画面を再描画するまで🔒が現れない**。
2. **ロックする操作が用意されていない**：現在は「個別編集で自動ロック」と
   「🔒クリックで解除」だけ。意図的にロックしたい／ロック状態を確認したいときの
   操作が無く、発見しづらい。

**改善方針**
- 各行の編集欄に**🔒トグルボタンを明示的に置く**（「この行を保護する」）。
  押せばロック／解除が切り替わり、状態が常に見える。
- 個別編集で自動ロックが付いた瞬間に、**その行だけ再描画して🔒を即座に出す**
  （全体再描画は重いので、対象行のバッジだけ更新する）。
- 自動ロックが付いたことが分かるよう、短時間ハイライトするなどの合図を出す。

### 34-5. GPTへの追加依頼（組版）
上記①②の適正値（許容行数・フォント縮小の下限・改行位置の優先順位・孤立行の扱い・
分割配置の縦位置とサイズ比と間隔）は私の推測でしかないため、
`GPT-依頼書.md`の追記5で問い合わせる。**回答を待ってから数値を確定する。**

## 35. 組版エンジンの設計（GPT分析の実装仕様・2026-07-28／未実装）

### 35-1. 1行あたりの最大文字数（GPT「1」）
| 有効幅 | 最大文字数 | 平均 |
|---|---:|---:|
| 画面いっぱい（80%） | 14〜18 | **16** |
| 画面の半分（40〜45%） | 8〜10 | **9** |
| 画面の1/3 | 5〜7 | **6** |

3点が**きれいな線形**に乗る（16/0.80=20、9/0.44≒20、6/0.33≒18）ので、
実装は次の1本の式にする。**これを超えたら改行を検討する（GPTでは約80%）。**

```
maxChars(widthRatio) = round(widthRatio × 20)
```

現在の配置スロットに当てはめた上限：
| slot | maxW | 1行の上限文字数 |
|---|---:|---:|
| fullWidth | 0.94 | 19 |
| bottomCenter / topCenter | 0.86 | 17 |
| center | 0.72 | 14 |
| CORNER各種 | 0.46 | 9 |
| left / right | 0.44 | **9** |

### 35-4. 改行位置の評価エンジン（GPT「4」「5」＋追加提案）

## 36. 文字デコ（打点）の品質問題（2026-07-28／原因調査済み・未修正）

「大きさがバラバラ／速度がバラバラ／チカチカ点滅する／ダサい」というフィードバックを調査した。
**実装バグと設計値の問題が混在している。**

### 36-1. チカチカ点滅 ← 実装バグ（原因特定）
**`renderLineList()`を1回呼ぶだけで、`resetDeco()`が15回、`drawFrame()`が
1.8秒〜193.2秒までバラバラの時刻で15回呼ばれている**ことを実測で確認した。

原因は`renderRowPreview()`（セクション見出しのサムネイル生成）が、
**メインcanvasに実際に`drawFrame()`して縮小コピーする**方式で、その前に
`resetDeco()`を呼んでいるため。ゾーンの数だけ繰り返される。

これにより：
1. `decoPops`（表示中のデコ）と`decoMark`（発生済みの記録）が**15回全消しされる**
2. グローバルな`lastT`がサムネの時刻（193.2秒）になり、次の本番描画で`dt`が異常値になる
3. `decoMark`が消えるため、**同じ文字のデコが何度も再発生する**

`renderLineList()`は編集のたびに呼ばれるため、**編集中はデコが点滅し続ける**。

**修正方針**：サムネイル生成を**メインcanvasとは別のオフスクリーンcanvas**で行い、
`decoPops`/`decoMark`/`lastT`といったグローバルな再生状態に一切触れないようにする。

### 36-2. 大きさがバラバラ ← 設計値の問題
`DECO_SIZE`の最大と最小の比が**約9.5:1**（集中線2.00 ／ 紙吹雪0.21）。
GPTの実測（19-2）に忠実に作ったが、**「デコの大きさ」スライダーが全種類に同じ倍率を
掛ける**ため、ユーザーが×2.7にすると**集中線が文字高さの5.4倍**（画面の大半）になる。
種類ごとの比率をそのままにしたまま全体を拡大すると破綻する構造だった。

### 36-3. 速度がバラバラ ← 設計値の問題
`DECO_LIFE`の最大と最小の比が**約4.6:1**（音符0.65秒 ／ キラッ0.14秒）。
同じ画面に速いものと遅いものが混在し、統一感を欠いている。

### 36-4. 色・形が「ダサい」 ← 主観の領域。GPTに問い合わせる
完全別色に使う`DECO_COLORS`（`#FF5FA2` `#2BA6F0` `#FFB020` `#3EC272` `#9A6BFF`）は
**彩度が高く、パステル調のステッカーや背景と質感が合っていない**可能性が高い。
また線の太さ・角の処理・塗りか線かといった「質感」の基準を持っていない。
ここは統計と美的判断が要るため、`GPT-依頼書.md`の追記6で問い合わせる。

### 36-5. 対応の切り分け
| 症状 | 種別 | 対応 |
|---|---|---|
| チカチカ点滅 | **実装バグ** | すぐ直せる（36-1） |
| 大きさのばらつき | 設計値 | GPT回答を待って基準を決める |
| 速度のばらつき | 設計値 | 同上 |
| 色・形がダサい | 主観・美的判断 | GPT回答を待つ（追記6） |
